Gene’s Text Concatenator – User Guide v0.7.0

Gene Boo, 2024, Jul 2026

A high‑performance, multi‑threaded tool for concatenating text files from a directory tree into a single portable archive (plain text or LLM‑friendly Markdown) and extracting them back into a full directory structure.
Version 0.7.0 adds intelligent file splitting (by size, file count, or number of parts), custom naming, and the ability to extract split archives.

Installation

The Text Concatenator is a completely portable, single‑file executable.
No installation or external dependencies are required.

  1. Download the appropriate binary for your platform:

    • Windows: TextConcatenator_v0.7.0_Portable.exe

  2. Place it anywhere – your desktop, a project folder, a USB drive, or even add it to your PATH for system‑wide access. It runs straight out of the box.

Quick Start

Concatenate the current directory with auto‑naming (uses folder name):

concat_text

If you are inside a folder called my_project, this creates my_project.txt containing all text files.

Markdown output, relative paths, and a file tree:

concat_text -r -f md --tree

Creates my_project.md (if in my_project/).

Split the output into 3 equal‑sized parts (Markdown):

concat_text -r -f md -n 3

Produces my_project_part001.md, my_project_part002.md, my_project_part003.md.

Extract a split archive:

concat_text -x --split my_project_part001.md restored/

Reads all parts (_part001, _part002, …) and restores the original files into restored/.

Use Cases

  • LLM Context Preparation – Combine your entire project into one Markdown file with syntax‑highlighted code blocks and a file tree. LLMs can easily consume the result.
  • Code Archiving / Sharing – Send a single file (or a few parts) instead of a zip. The recipient can extract the original structure.
  • Large Project Splitting – Break a huge concatenated output into manageable chunks (by size or number of parts) for easy upload or email.
  • Duplicate / Backup – Create a snapshot of a codebase, then later extract it to another location.
  • Filtering – Include only certain file types (e.g., *.rs, *.toml) or exclude logs and binaries.
  • Portable Documentation – Merge multiple text resources (notes, configs, logs) into one scrollable document.

Command‑Line Interface

concat_text [OPTIONS] [POSITIONAL...]

The first positional argument changes meaning depending on mode:

Mode Positional 1 Positional 2
Concatenation Starting directory Output file
Extraction Input archive file Output directory

If omitted, defaults are:

  • Start dir = current directory
  • Output file = automatically named (see Naming the Output)
  • Extraction output dir = current directory

Concatenation Mode

Flag / Option Description
--format, -f Output format: txt (default) or md / markdown.
--relative, -r Store file paths relative to the starting directory (portable).
--tree (Markdown only) Prepend a directory tree.
--include PATTERNS Only process files that match any of these comma‑separated patterns.
--exclude PATTERNS Skip files that match any of these patterns.
--include-file FILE Read include patterns from a file (one per line).
--exclude-file FILE Read exclude patterns from a file.
--name NAME Set base name for the output file(s). If not given, uses the directory name.
--split-size SIZE Split output into parts of at most SIZE (e.g., "2 MB", "1024kb").
--split-files N Start a new part every N files.
--split-into, -n K Split the final output into exactly K equal‑sized parts (by size).

Note: If both --include and --exclude are used, the last one wins (they set the mode). You cannot combine include and exclude in a single run.

Extraction Mode

Activated with --extract or -x.

Flag / Option Description
--format, -f Force input format (txt or md). If omitted, auto‑detected.
--output-dir, -o Directory where files will be extracted (default: current dir).
--split Treat the input file as the first part of a split archive.

Note: --relative and --tree have no effect in extraction mode.

Filtering Options (concatenation only)

Filtering works by matching patterns against file names, extensions, and paths. Details in How Filtering Works.

Format & Path Options

  • --relative / -r – When concatenating, file headers will show relative paths (e.g., src/main.rs instead of /home/user/project/src/main.rs). This makes the archive portable and allows extraction under any directory. In Markdown mode, all paths are written with forward slashes.
  • --tree – (Markdown only) Adds a pretty‑printed directory tree at the top of the output, inside a text code block.

Splitting the Output

You can split the concatenated result into multiple part files. The parts are named with a _part001, _part002, … suffix before the file extension.

  • By file size: --split-size "2 MB" or --split-size 1024kb. The size parser understands b, kb, mb, gb and allows decimals (e.g., 1.5 MB).
  • By file count: --split-files 50 starts a new part after every 50 files have been written.
  • By number of parts: --split-into 3 (or -n 3) will create exactly 3 parts, dividing the final archive into byte‑even chunks. This is the simplest way to split for sharing.

All split modes write a small temporary file during concatenation, then split it at the end – the temporary file is deleted automatically. For the --split-into option, if the total size is 0 (no files), empty part files are still created.

Naming the Output

By default, the tool uses the name of the directory being scanned as the base name for the output file(s). For example, if you run the tool inside parquet_viewer/:

concat_text -f md -n 3

produces parquet_viewer_part001.md, parquet_viewer_part002.md, parquet_viewer_part003.md.

You can override this with --name:

concat_text --name project_backup -f md -n 3

will create project_backup_part001.md, etc.

If a starting directory is given explicitly (e.g., ../some_folder), its leaf name is used. When no explicit output file name is provided, the extension is chosen automatically based on the format (.txt or .md). You can still specify a full output file name as the second positional argument to override the automatic naming.

Pattern Files

Instead of typing many patterns on the command line, you can use --exclude-file or --include-file. The file is read line by line; empty lines and lines starting with # are ignored.

Example exclude.txt:

# Ignore build artifacts
target
*.log
*.o

How Filtering Works

Patterns are case‑insensitive and match using these rules:

  1. Exact filename – "Cargo.toml" matches exactly.
  2. Extension – ".rs" or "rs" matches any file with that extension (e.g., main.rs).
  3. Path contains – "src" matches any file whose full path contains src.
  4. Filename contains – "test" matches my_test.rs because the filename contains test.

In Include mode, only files that match at least one pattern are processed.
In Exclude mode, all files are processed except those that match any pattern.

If no patterns are given, Include/Exclude mode act as normal (all files allowed).

Binary File Detection

To avoid corrupting the output, the tool automatically skips binary files:

  • By extension – A list of known binary extensions (e.g., exe, jpg, zip, pdf) is hard‑coded. Files with these extensions are immediately rejected.
  • Content sampling – The first 512 bytes are examined. If a null byte (0x00) is found, the file is binary. If more than 30% of the bytes are non‑printable control characters, it is also considered binary.

Empty files are treated as text.

Output Formats

Plain Text (.txt)

Each file is preceded by a header of 80 equal signs:

================================================================================
path/to/file.txt
================================================================================
file contents...

This format is easy to parse manually and is the default.

Markdown (.md)

Designed for LLM consumption. Each file becomes:

## `path/to/file.rs`

```rust
fn main() {}


- The heading contains the path in backticks.
- A fenced code block with an **auto‑detected language** (based on file extension) follows.
- A horizontal rule (`---`) separates files.

If `--tree` is used, a directory tree is added at the top:

File tree

.
├── src/
│   ├── main.rs
│   └── lib.rs
├── Cargo.toml
└── README.md


Supported languages include: Rust, Python, JavaScript, TypeScript, HTML, CSS, JSON, XML, Markdown, Bash, TOML, YAML, Java, Go, C/C++, Ruby, PHP, Swift, Kotlin, Scala, SQL, and more. Unknown extensions get an empty language tag (plain code block).

---

## Extraction Details

To extract files from a concatenated archive:

```bash
concat_text -x archive.txt [output_dir]

or

concat_text -x -f md archive.md output/
  • The tool automatically detects the format unless you force it with --format.
  • TXT extraction looks for lines consisting of exactly 80 = signs, then reads the path line, then the next separator, and finally the content until the next separator.
  • Markdown extraction looks for level‑2 headings (##) followed by a code fence (```). It captures everything until the closing ```.
  • Paths stored in the archive may be absolute (default) or relative (if --relative was used during concatenation). During extraction, absolute paths are made safe by stripping the leading root component (e.g., / or C:\), so they become relative. This prevents accidentally writing outside the chosen output directory.
  • Parent directories are created automatically.

Extracting split archives

If you used any split mode during concatenation, you must use the --split flag when extracting. Point to the first part file (e.g., my_project_part001.md), and the tool will automatically find and read all consecutive parts (_part002, _part003, …). The entire archive is then restored as if it were a single file.

Example:

concat_text -x --split bundle_part001.md restored/

Examples

Concatenation

1. Plain text, absolute paths, auto‑named (current folder):

concat_text

If the current folder is myapp, creates myapp.txt.

2. Markdown with relative paths, tree, and custom name:

concat_text -r -f md --tree --name project_docs ./src

Writes project_docs.md containing all files under ./src.

3. Split into 3 equal parts (Markdown, relative paths):

concat_text -r -f md -n 3

Produces currentfolder_part001.md, _part002.md, _part003.md.

4. Split by size (5 MB chunks):

concat_text -r -f md --split-size "5 MB" ./src

5. Include only Rust and TOML files:

concat_text --include "rs,toml" . rust_code.txt

6. Exclude log files and node_modules:

concat_text --exclude "*.log,node_modules" . clean.txt

Extraction

7. Auto‑detect format and extract to current directory:

concat_text -x bundle.txt

8. Force Markdown format and extract to restored/:

concat_text -x -f md bundle.md restored/

9. Extract a split archive:

concat_text -x --split my_project_part001.md extracted/

Performance

  • Files are collected and checked for binary content in parallel using Rayon.
  • Large files (>1 MB) are read with memory mapping; small files use buffered I/O.
  • Output writes are serialised behind a mutex, but the processing (reading, decoding, header generation) happens in parallel.
  • The binary can be compiled with maximum optimisations (lto = true, opt-level = 3).

Typical performance: concatenating thousands of files from an SSD takes only a few seconds.

Notes & Limitations

  • The tool assumes UTF‑8 encoding for all text files. Non‑UTF‑8 files may be transcoded lossily via String::from_utf8_lossy when using memory mapping, or correctly decoded via encoding_rs for buffered reads.
  • Symbolic link cycles are prevented during directory traversal (visited set).
  • The TXT extraction split method reads the entire input file into memory. For extremely large archives (>several GB), ensure sufficient RAM.
  • Markdown code fences can be nested only if the file itself contains ``` lines – those would break extraction. This is rare for source code.
  • The filter pattern * is not a wildcard; it is a literal character. To match any extension use just the extension name (e.g., rs).
  • The tool does not currently support appending to an existing output file; it always overwrites.
  • When using --split-into N, the splitting is purely byte‑based; file boundaries may appear in the middle of a file’s header/content within a part. Extraction from split parts reassembles the original stream seamlessly.
